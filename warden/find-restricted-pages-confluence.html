How to find every restricted page in Confluence Cloud

Confluence Cloud has no site-wide list of restricted pages. Admins have been asking for one since 2013 and the requests are still open. This page sets out exactly what you can see natively, what you cannot, what Atlassian is currently building, and how to inventory the lot.

A page restriction in Confluence narrows who may view or edit a single page, inside whatever the space already permits. Restrictions can be set directly on a page or inherited from an ancestor, so a page can be restricted without carrying any restriction of its own.

Confluence Cloud shows you a page’s restrictions one page at a time, and offers a per-space list. It provides no view across the whole site — there is no admin screen that answers “which pages on this site are restricted, and to whom?”. That gap is what this page is about.

01

What you can see natively

One page at a time

Open a page, click the restrictions (padlock) control, and you see who can view and edit it, including whether the restriction came from an ancestor. This is accurate and complete for that page. It does not scale: answering “are we exposed anywhere?” by opening pages one by one is not an audit, it is a sampling exercise you will abandon.

Per space

Space settings include a restricted-pages view scoped to that space. Useful, and the closest native equivalent to what people want — but you must know which space to look in, and you must repeat it for every space on the site. On a Confluence instance with a few dozen spaces this is a morning’s work that is out of date by the afternoon.

Space permissions are a different thing

Worth separating clearly, because it is the most common confusion. Space permissions decide who can get into a space at all. Page restrictions narrow that set for individual pages. Reviewing space permissions tells you nothing about which pages inside are restricted, and vice versa. A complete access picture needs both.

The thing that surprises people: a site administrator cannot necessarily read a page restricted away from them. Restrictions are not an admin-override permission — which is exactly why the ability to at least see which pages are restricted has been requested for so long.

The one that is In Progress deserves a straight answer

CONFCLOUD-76815 — a REST API returning a list of restricted pages — is marked In Progress. That is worth knowing before you buy anything, so here is the honest reading of it.

It is a building block for developers, not a report for administrators. An endpoint returning restricted pages does not tell you that a restriction points at a deactivated user, does not tell you what changed since your last review, and does not produce a CSV your auditor will accept. It is the raw material.

If you are comfortable writing a script, and all you need is the raw list, that API may well be enough for you once it ships — and you should not buy an app to get something the platform is about to hand you. That is the genuine case for waiting.

If you need the interpretation rather than the data — which restrictions are broken, what changed since last quarter, an export somebody else will read — that is a different job, and the API landing makes tools that do it more accurate rather than redundant.

03

Why the answer drifts even when nobody edits a page

The reason a one-off audit does not stay true: restrictions name users and groups, and users and groups change underneath them. A restriction set correctly two years ago can be wrong today without anyone touching the page.

  • Someone was deactivated. The restriction still names them. They cannot read the page, but they are still listed as though they can — and if they were the only person granted access, nobody can now read it.
  • A group was emptied. The restriction points at a group that no longer has members. It looks like a valid restriction and grants access to nobody.
  • A user or group was deleted. The restriction now names a principal that does not exist at all.
  • Inheritance carried it further than intended. A restriction placed on one parent page silently applies to every page created beneath it afterwards, including pages the original author never saw.

The compounding case is the worst one: if the page that everyone inherits from ends up with no live viewer, every descendant is stranded too — content that exists, that people expect to find, and that only a site admin can now reach.

04

Inventorying the lot with Warden

Warden is Slate’s access audit app for Confluence. It does one job: it inventories every view- or edit-restricted page across the whole site and flags the restrictions that have gone wrong. It is read-only — there is no write scope in its manifest at all, so it cannot change a restriction even if you asked it to.

  • The inventory. Every restricted page on the site, who can view and edit it, and whether the restriction is set directly on the page or inherited — with the ancestor it came from.
  • Red flags. Restrictions naming a deactivated user, an empty group, or an orphaned principal that no longer exists — plus the page-level consequence, no live viewer or no live editor, where every grantee is dead and the page is stranded.
  • What changed since last time. From the second scan onwards, a banner reports how many red flags are new and how many were resolved, and each new finding carries a New marker. A quarterly review starts from the diff rather than re-reading the whole inventory.
  • A daily re-scan, plus scanning on demand. Scans run in the background so large sites do not time out.
  • CSV export of the inventory and of the red flags, UTF-8 with a byte-order mark so it opens cleanly in Excel and Google Sheets.

Run it from Confluence Settings → Apps → Warden — Access Audit.

05

What it will not do

Stated plainly, because these are the things people assume and then feel misled about.

  • It is not a historical change log. A Forge app cannot reconstruct who changed a restriction before it was installed. The “since last scan” diff begins at your second scan — there is nothing to compare against before that.
  • It does not fix anything. No remediation, no bulk edit, no “clean up” button. The manifest carries no write scope. You act on the evidence.
  • It does not make you compliant. It produces evidence for a review that a human still performs and signs off.
  • Deactivated-user detection is best-effort under the Runs on Atlassian constraints. Empty-group and orphaned-principal flags are exact.
  • Very large sites hit a page cap, and the report says so with a partial badge rather than pretending it saw everything.
  • Slate is not Cloud Fortified. If your procurement process requires it, Warden does not qualify today.

Questions

Can I see all restricted pages in Confluence Cloud natively?
Not across the site. You can view restrictions on one page at a time, and there is a restricted-pages view per space, but Confluence Cloud provides no site-wide list. Requests for one have been open on Atlassian’s public tracker since 2013.
Can a site admin see pages that are restricted away from them?
Not necessarily — page restrictions are not overridden by site administration. This is precisely why the ability to at least enumerate restricted pages has been requested for so long.
Is Atlassian building this?
Partly. CONFCLOUD-76815, a REST API returning a list of restricted pages, is marked In Progress. That is a developer building block rather than an admin report — it returns data, not an interpretation of it. If you can write a script and only need the raw list, it may be all you need.
What is the difference between space permissions and page restrictions?
Space permissions decide who can enter a space. Page restrictions narrow that set for individual pages, and can be inherited by child pages. Reviewing one tells you nothing about the other.
Why would a restriction be wrong if nobody edited the page?
Because restrictions name users and groups, and those change. Someone is deactivated, a group is emptied, a principal is deleted — the restriction is untouched but no longer means what it did.
Does Warden change my restrictions?
No, and it could not. Its manifest declares no write scope for Confluence content, so modifying a restriction is not something it is capable of. It reports and flags only.
Does my page content leave Atlassian?
No. Warden carries the Runs on Atlassian badge — it runs inside your own Atlassian cloud with no external servers, and the snapshot it builds is stored in Atlassian-hosted storage in your tenant.
